# Наши лайфхаки

Эти приёмы появились из практики работы с AI-агентами. Здесь универсальные выводы:
без клиентских историй, внутренней инфраструктуры и рабочих данных.

## 1. Сначала разведка, потом создание

Перед новым скриптом ищем существующий инструмент. Перед новой папкой читаем текущие
инструкции и историю. Новое название задачи часто скрывает уже решённую проблему.
Проверка: можете назвать, что переиспользуете и зачем всё же нужна новая часть.

## 2. Развести смысл, состояние, правила и структуру

README объясняет цель; state ведёт к текущей работе; AGENTS определяет поведение;
карта показывает код. Не копируем один длинный текст в четыре документа.
Это позволяет обновлять каждый слой в своём темпе.

## 3. State — указатель, а не дневник

Один следующий шаг плюс ссылки лучше большой простыни. История — в коммитах и журнале,
подробный план — в документе задачи. Если next_action занимает страницу, это уже план.

## 4. Свежесть по SHA, а не по сегодняшней дате

Дата обновления может быть новой, а текст — старым. `head_sha` привязывает состояние
к коммиту; проверка истории показывает, появился ли после него новый код.
Так «посмотрел сегодня» не превращается в ложное «соответствует новой версии».

## 5. Один писатель избавляет от войны PR за state

Каждая feature-ветка меняет своё содержимое, а следующий шаг пишет в PR. Общий state
обновляют на основной ветке после merge. Иначе все PR конкурируют за одни строки.

## 6. Политика общая, команды проектные

Общие правила Git/секретов должны иметь один источник. Команды тестов, стек и границы
конкретного проекта нельзя заменить универсальным шаблоном. Линтер показывает дрейф;
он не должен молча стирать локальное решение.

## 7. Не утверждать больше, чем проверено

Локальные тесты доказывают локальные тесты. Коммит доказывает сохранение изменений.
Deployment требует проверки установленной версии и живого результата. В отчёте:
«проверено X командой Y; Z не проверено». Это полезнее уверенного «всё готово».

## 8. Хук должен делать меньше, чем агент

Хук даёт быстрый сигнал: секрет, невалидный state, устаревший anchor. Он не должен
публиковать, перезапускать сервис, тратить деньги или автоматически принимать решение.
Тяжёлые тесты — в CI/явной команде; быстрые проверки — рядом с изменением.

## 9. Отказ при конфликте лучше скрытой замены

Если pre-commit уже занят, installer останавливается до изменений. Это повод
прочитать существующий workflow и вручную объединить вызовы. «Удобная» перезапись
может отключить важную чужую проверку незаметно для владельца.

## 10. Проверять неудобные сценарии

Тестируем не только пустой новый проект: существующие правила, путь с пробелами,
повторную установку, изменённый хук, feature-ветку, staged/working-tree расхождение,
отсутствующий инструмент. Именно здесь ломаются переносимые пакеты.

## 11. Не путать timeout с доказанным отказом

Во внешних операциях отсутствие ответа не доказывает, что операция не состоялась.
Записываем «неизвестно», проверяем результат по устойчивому ID и не повторяем вслепую.
Этот kit сам внешние операции не выполняет; правило пригодится вашему агенту.

## 12. Публичная версия получает чистую историю

Публикуем проверенный набор файлов в новом репозитории, без старых архивов и рабочих
данных. Сканируем файлы, diff и всю историю, затем проверяем опубликованную копию.
Секреты и личные сведения — разные классы: для второго нужен отдельный просмотр.

## 13. Не добавлять автоматику раньше пользы

Сначала стандарт помогает в нескольких реальных задачах. Затем обязательные проверки.
Нельзя считать внедрением просто наличие AGENTS, пустых правил и зелёного бейджа.

## 14. Автоматическая карта хранит человеческие пояснения

Генерируем факты из кода; объяснения и ограничения редактируем отдельно. При повторной
генерации ручные разделы нужно сохранять. Проверка этого поведения входит в тесты kit.
