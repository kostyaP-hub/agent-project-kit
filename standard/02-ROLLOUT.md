# Внедрение в существующие проекты

Это инструкция для человека и агента. Внедрение начинается с чтения, а не с установки.

1. Назовите разрешённые папки и владельцев. Не сканируйте домашнюю папку по умолчанию.
2. Инвентаризируйте AGENTS, обёртки, rules, state, команды проверки и Git-хуки.
3. Покажите diff-план. Не меняйте upstream-клоны, production, чужие файлы и глобальные настройки.
4. Начните с одного проекта. Для существующего AGENTS используйте `--additive`.
   Этот режим сохраняет существующие rules; дрейф показывается lint, а не исправляется молча.
5. Полный CLAUDE.md переносите только после просмотра: если AGENTS уже существует,
   не заменяйте его. Объедините правила вручную, сохранив их смысл и происхождение.
6. Заполните проектные правила фактами. Команды-заглушки не считаются работающим workflow.
7. Добавьте state и знание о проекте; соблюдайте правило единственного писателя.
8. Запустите validator, lint и реальные project checks; закоммитьте свои файлы поимённо.
9. Хуки подключайте отдельной явной командой, сначала `--dry-run`.
10. Следующий проект — после проверки первого. Для больших изменений оставьте список исключений.

Для fleet-аудита можно явно настроить `~/.ctx/config.json`:

```json
{
  "scan_roots": ["~/projects"],
  "owned_namespaces": ["your-account"],
  "knowledge_root": null,
  "knowledge_entity_glob": "projects/*.md",
  "extra_roots": [],
  "extra_namespaces": [],
  "excluded_paths": []
}
```

`ctx-lint.py --all --scorecard` читает этот конфиг. Пустой список означает «не настроено».
Инструменты kit не выполняют ownership-enforcement при каждом write: владелец обязан
выбрать разрешённую цель перед запуском scaffold/install. Fleet ownership check — подсказка.
Ни один этап не разрешает автоматически push, внешние публикации или платные действия.
