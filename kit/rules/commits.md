# Правило: коммиты (commit-or-die)

## Commit ≠ push: разный риск — разный гейт

**`commit` — по умолчанию ДА, без спроса. `push` / PR / merge / tag — ВСЕГДА спрашивать.**

Причина расщепления: гейт «спроси человека» написан под необратимое-и-наружу. Локальный
коммит на своей ветке ни то, ни другое — он обратим (`reset`, удалить ветку), никому не
виден, не запускает CI и не выкатывает. Push — виден команде, дёргает CI/PR, иногда
деплой. Запрещать их одним правилом значит платить потерей точек отката за безопасность,
которой коммит и так не угрожает.

Коммичу сам, когда выполнены ВСЕ условия:

1. verification-гейт зелёный (см. ниже: после `verify GREEN`, не до);
2. только свои файлы, поимённо — **никогда `git add -A`**;
3. своя feature-ветка;
4. никаких `amend` / `force` / rebase уже опубликованного;
5. preflight на секреты до `git add` (`repo-preflight.sh`, `git diff --cached`).

**Спрашивать всегда, независимо от условий:** push, PR, merge, tag; плюс любой коммит
в чужом репозитории и в клоне чужого проекта.

**Про `main` — по типу репозитория, не бланкетно.** Там, где работа идёт через ветки и
Pull Request (защищённый `main`), коммит прямо в `main` запрещён. В личных проектах без
ветвления коммит в `main` легитимен — там пункт 3 читается как «на текущей рабочей ветке».

## Как коммитить

- **Коммить после каждого успешного шага.** Десять промптов без коммита = потерянный день. Малыми коммитами.
- Один логический шаг = один коммит. Не мешай рефакторинг с фичей.
- Коммить после `verify GREEN` (тесты прошли), не до. RED-коммит отдельно — это ОК.
- Зачем: точечный откат к рабочему состоянию; видно, что изменила модель vs ручные правки; `git bisect` работает; при фейле не теряется час.
- Сообщение: **почему** менялось, а не пересказ диффа.
- Перед «готово» — свежая проверка: утверждение = команда + её код возврата + ключевой вывод. Не «должно работать».
